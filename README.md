# Мониторинг лотов goszakup

Находит лоты на портале госзакупок РК по нашему списку ЕНСТРУ, у которых **0 заявок**
и скоро истекает приём, и присылает их в Telegram менеджерам — так, чтобы
уведомление пришло в рабочее время и с запасом на подготовку.

## Запуск

```bash
python -m venv .venv
.venv\Scripts\pip install -r requirements.txt
.venv\Scripts\python run.py
```

Админка: <http://127.0.0.1:8765> (только localhost, наружу не смотрит).

## Токен

Токен API goszakup вводится **вручную в админке** и сохраняется в
`config/settings.local.json`. Этот файл в `.gitignore` — в репозиторий он не попадает.
В браузер токен возвращается только замаскированным (`abcd••••••••1234`).
Чтобы не менять сохранённый токен — оставьте поле пустым.

## Список ЕНСТРУ

Берётся из Google-таблицы, ссылка настраивается в админке. Пополнять список можно
прямо в таблице, код трогать не нужно. Таблице нужен доступ
«Просматривать могут все, у кого есть ссылка».

Текущая таблица: 147 строк, 89 уникальных позиций (серверы, коммутаторы,
маршрутизаторы, ПАК, ИБП, услуги сопровождения).

## Как это работает

```
Google-таблица (128 кодов)
  -> Plans(refEnstruCode).RefEnstru      ОФИЦИАЛЬНОЕ название позиции (89 штук)
  -> Lots(nameDescriptionRu: название)   ищем кандидатов (другого фильтра нет)
  -> window.should_alert() + сумма       пора ли уведомлять и стоит ли того
  -> pointList -> Plans.refEnstruCode    РЕШАЕТ КОД: наш -> берём, чужой -> мимо
  -> (код не сверился) точное имя        запасной критерий + отсев мусора
  -> portal.application_count()          число заявок — только с публичной страницы
  -> заявок <= порога  =>  Telegram      один раз на лот
```

Полный обход занимает ~2–3 минуты.

### Названия берём у площадки, а не из таблицы

Таблица — источник **кодов**. Как позиция называется, знает только площадка:
`Plans(refEnstruCode: код).RefEnstru.nameRu`. По этим названиям и ищем.

Иначе теряются целые позиции: 7 кодов из 128 названы в таблице сокращённо, и на
портале таких названий просто нет.

| Код | В таблице | Официально |
|---|---|---|
| `620220.000.000000` | Услуги консультационные в области **ИТ** | …в области **информационных технологий** |
| `620920.000.000011` | Услуги по восстановлению **ПО**/… | …по восстановлению **программного обеспечения**/… |
| `802010.000.000004` | Услуги по **техобслуживанию**… | …по **техническому обслуживанию**… |
| `264033.900.000000` | Комплекс оборудования **видеонаблюдения** | Комплекс оборудования |

Переход на официальные названия поднял охват с 256 до **309** активных лотов.
Расхождения показываются в админке после «Проверить сейчас» — таблицу можно
поправить, но система работает и так.

Названия справочника стабильны, поэтому кэшируются в `enstru_cache` навсегда.

### Решает код ЕНСТРУ, а не название

Название — только способ найти кандидатов: другого серверного фильтра у `Lots` нет.
Критерий отбора — код через пункт плана (`Lots.pointList` → `Plans(id).refEnstruCode`).

Порядок именно такой, потому что **название лота не обязано совпадать с названием
позиции**. Пока имя было главным критерием, аудит находил 5 потерь на 256 лотов.

Код сверяется примерно у 95% лотов. У остальных пункт плана ещё не попал в индекс
`Plans` — там запасной критерий, точное совпадение названия. Он нужен потому, что
`nameDescriptionRu` ищет и по характеристике: запрос «Сервер» вытаскивает лоты
чужих позиций, где сервер лишь упомянут в описании.

> Не путать с настоящими позициями заказчика, которые звучат неожиданно.
> «Комплекс медицинский» (`262015.000.000018`) — строка 17 таблицы: аппаратно-
> программный комплекс с сервером базы данных. Это не мусор, а их профиль.

### Проверка, что лоты не теряются

Независимый обход, не использующий поиск по названию вообще:
`Plans(refEnstruCode: код)` → id пунктов плана → `Lots(pointList: id)`.
По пяти кодам он нашёл 32 активных лота — **все до единого есть в основной выдаче**.

Этот путь непригоден как основной (тысячи пунктов плана на код = тысячи запросов),
но годится как контроль. Повторять при сомнениях, что охват просел.

### Почему не через `Lots.enstruList`, хотя поле создано ровно для этого

**Оно не заполнено.** Замер: из 200 лотов «Коммутатор сетевой» у 199 там `[0]`,
реальный код проставлен у одного. Отбор по нему находил **2 лота** на все 128 кодов
вместо 245 — и выглядел при этом совершенно правдоподобно.

## Окно уведомления

**Текущая настройка: запас 48 ч, поправка на рабочие дни ВЫКЛЮЧЕНА** — так решил
заказчик 2026-07-17, осознанно (см. компромисс ниже).

Уведомление уходит ровно за `window_hours_min` часов до конца приёма.

### Компромисс с выходными

Дедлайнов на выходных практически нет (сб 18, вс 7 из 3272), а на пн/вт приходится
половина всех. Поэтому:

- лот с дедлайном в **понедельник 14:00** → 48 часов до него = **суббота 14:00**;
  уведомление уходит в выходной, менеджер видит его утром понедельника, когда
  осталось пара часов;
- в **пятницу вечером выдача почти пустая**: окно 48 ч = суббота + воскресенье,
  а на эти дни дедлайнов не ставят. Это не поломка.

Заказчик выбрал буквальные 48 часов, зная про это.

### Если понадобится вернуть поправку

Галочка `respect_working_hours` в админке. С ней момент уведомления сдвигается
назад до начала последнего рабочего дня, с которого запас ещё соблюдается:

- дедлайн **четверг 10:00**, запас 24 ч → уведомление **среда 10:00** (ровно сутки);
- дедлайн **понедельник 09:00** → уведомление **пятница с утра**, а не в воскресенье.

Цена: цифра часов в сообщении становится большой (70+ ч для понедельничного лота),
и это выглядит как ошибка, пока не посмотришь на дату дедлайна. Поэтому в сообщении
теперь стоит день недели: «до пн 20.07 в 14:00 · осталось 69 ч».

Инвариант, покрытый тестами: с поправкой запас никогда не меньше заданного, и момент
уведомления всегда попадает в рабочее время. Проверено перебором всех дедлайнов
на две недели.

## Пороги отбора

**`max_applications`** — `0` означает только нулевую конкуренцию, как в ТЗ.
Больше нуля — режим «низкая конкуренция», он же удобен для проверки системы
на живых данных.

Замер за 7 дней (245 лотов в окне): 0 заявок — 146 лотов, 1 — 52, 2 — 13,
3 — 3, 4 — 2, 5 — 8. Счётчик живой и различающий.

**`min_amount`** — минимальная плановая сумма лота, по умолчанию 2 млн ₸.
Без неё выдача забивается мелочью на 18–60 тысяч. Замер за один проход:

| | Лотов в окне | С 0 заявок | Сообщений | Медиана суммы |
|---|---|---|---|---|
| Без фильтра | 150 | 64 | 7 | 208 448 ₸ |
| От 2 млн | 25 | 13 | 2 | 16 359 000 ₸ |

Если сумма лота неизвестна, а порог задан — лот пропускается: гадать при
заданном пороге хуже, чем промолчать.

Влияние запаса на объём (пятница, первый проход; дальше только новые лоты
за счёт дедупликации):

| Запас | Лотов в окне | С 0 заявок |
|---|---|---|
| 24 ч | 158 | 70 |
| 40 ч | 209 | 109 |

## Память об отправленном

**Помним лот, пока идёт приём заявок. Закрылся — забываем.**

Пока приём открыт, лот попадает в каждый проход: без памяти менеджеры получали бы
его каждые два часа. Как приём закончился, запись — мёртвый груз: отправлен этот
лот больше не будет в любом случае (`window.should_alert` отсекает закрытые).
Чистка идёт в начале каждого прохода, `store.purge_closed()`.

Привязка именно к дедлайну лота, а не к фиксированному сроку. Срок в 24 часа
переслал бы **ещё открытый** лот повторно: показанный в пятницу лот с понедельничным
дедлайном вернулся бы в субботу. Итог правила — ровно одно уведомление на лот.

Настройки у этого нет: правило не про вкус, а про корректность.

## Когда площадка недоступна

goszakup регулярно деградирует (отдаёт HTTP 500 или таймаутит) — это её норма,
проверено вживую. Система на это рассчитана:

- **Предохранитель.** Клиент ретраит каждый запрос, поэтому при массовом 500 обход
  89 позиций растянулся бы на ~45 минут. Если 5 запросов подряд упали и ни один не
  прошёл — проход прерывается сразу (`PLATFORM_DOWN_STREAK` в `monitor.py`).
- **Быстрый повтор.** Упавший проход не ждёт до завтрашних 09:00, а повторяется
  через 20 минут (`RETRY_AFTER_FAILURE`). Ожившую через час площадку поймаем в тот
  же день, а не через сутки.
- **Алерт по смене состояния.** Первый сбой — красное «не удалось проверить»;
  восстановление — зелёное «связь восстановлена». Повторы каждые 20 минут молчат,
  чтобы при многочасовом простое не спамить.

## Датчик жизни

**`daily_report`** (включён) — сводка уходит даже когда лотов не нашлось.

Это не отчётность. При запасе 48 ч пустая пятница — норма (окно упирается в
выходные), поэтому **молчание сломанного сервера неотличимо от молчания спокойного
дня**. Особенно важно на офисном железе: пропало питание или интернет — и никто
не заметит, пока не выяснится, что тендеры уходят мимо.

Пришла утренняя сводка — система жива. Не пришла — идти чинить.

## Интервал скана

**Текущая настройка: раз в сутки в 09:00 по Астане при запасе 48 ч.**

Время фиксированное (`daily_scan_at`), а не «через 24 часа после прошлого раза».
Иначе перезагрузка сервера после сбоя питания в 3 ночи навсегда переносит скан
на 3 ночи — и лоты приходят, когда все спят. Покрыто тестами: сколько ни
перезапускай, скан остаётся в 09:00.

С памятью об отправленном не связан: от повторов защищает память, а не редкий скан.
Зато он напрямую определяет, сколько времени реально остаётся у менеджера:

```
худший запас у менеджера = window_hours_min − poll_interval
```

Сейчас: 48 − 24 = **24 часа в худшем случае**. Обещание держится.

Почему суточный скан требует запаса именно 48, а не 24 — смоделировано на лоте
с дедлайном в среду 10:00 при запасе 24 ч:

| Интервал скана | Когда уведомит | Осталось до дедлайна |
|---|---|---|
| 24 ч (скан в 09:00) | ср 09:00 | **1 ч** — провал |
| 24 ч (скан в 17:00) | вт 17:00 | 17 ч — в обрез |
| 2 ч | вт 11:00 | 23 ч — как обещано |

Админка считает худший случай прямо под полем интервала и краснеет, если обещание
перестаёт выполняться.

## Почему дайджест, а не сообщение на лот

Telegram режет примерно на **20 сообщениях в минуту** в одну группу. Первый проход
находит сотню лотов — по одному их слать нельзя, половина не дойдёт с 429.
Поэтому: до 5 лотов — отдельными сообщениями, больше — дайджест пачками по 10
(`app/notify.py`, покрыто тестами).

Отметка «отправлено» ставится в базу только **после** успешной отправки: если
Telegram упадёт, лот попадёт в следующий проход, а не потеряется навсегда.

## Перенос на другой компьютер (Windows)

**На этом компьютере** — собрать пакет:

```powershell
powershell -ExecutionPolicy Bypass -File deploy\make-package.ps1
```

Появится `goszakup-monitor-ГГГГ-ММ-ДД.zip` (~75 КБ). В него входят только код,
тесты и документация. Токены, база и выгрузки **не входят** — сборка проверяет это
и отменяется, если секрет всё же попал внутрь.

**На новом компьютере** — распаковать архив и выполнить в его папке:

```powershell
powershell -ExecutionPolicy Bypass -File deploy\setup-windows.ps1
```

Установщик проверит Python (нужен 3.11+), создаст окружение, поставит зависимости,
**прогонит тесты** и заведёт автозапуск при входе в систему. Права администратора
не нужны.

Дальше — открыть <http://127.0.0.1:8765> и ввести токены заново: токен площадки,
токен Telegram-бота и Chat ID. Они намеренно не переносятся.

История отправок тоже не переносится, поэтому при первом проходе на новом
компьютере придут все актуальные лоты.

### Что выяснилось при проверке установки

Прогон на чистой копии поймал три вещи, которые сломали бы установку у вас:

- **`pytest` не входил в `requirements.txt`** — на моей машине он стоял вручную,
  а на чистой шаг проверки падал. Вынесен в `requirements-dev.txt`.
- **PowerShell 5.1 читает `.ps1` без BOM как ANSI** — кириллица в скриптах
  превращалась в мусор, и парсер отказывался их запускать. Файлы сохранены с BOM.
- **`schtasks /create` не принимает команду длиннее 261 символа** — на длинном
  пути установки автозапуск молча не создавался. Заменено на
  `Register-ScheduledTask`, у которого этого предела нет.

### Ограничение домашнего компьютера

Пока машина выключена или спит, проверки не идут: планировщик наверстает
пропущенный скан при следующем входе в систему, но время будет упущено.
Для круглосуточной работы нужен сервер — см. следующий раздел.

## Установка на сервер

**Ubuntu Server 24.04 LTS** (Python 3.12 уже в системе) + systemd. Железо: любое,
приложение занимает ~60 МБ и просыпается раз в сутки на 2–3 минуты.

```bash
git clone <репозиторий> && cd goszakup-monitor
sudo bash deploy/install.sh
```

Скрипт создаёт системного пользователя `goszakup` без shell, кладёт приложение в
`/opt/goszakup-monitor`, собирает venv, ставит юнит и включает автозапуск.

### Админку наружу не выставлять

**В админке нет авторизации.** Она безопасна только потому, что слушает `127.0.0.1`.
Кто достанет до порта — сменит chat_id на свой и будет получать ваши лоты, подменит
ссылку на таблицу или тихо сломает отбор.

Доступ со своего ноутбука — SSH-туннелем, без открытых портов и паролей:

```bash
ssh -N -L 8765:127.0.0.1:8765 user@server
```

Дальше <http://127.0.0.1:8765> в браузере. Закрыли туннель — админка недоступна.

### Что даёт юнит

`Restart=always` — пропало питание в офисе, машина поднялась, сервис встал сам.
Проверьте заодно в BIOS «Power On After Power Loss», иначе сервер просто не включится.

Ограничения (`ProtectSystem=strict`, `NoNewPrivileges`, `ProtectHome`) закрывают
всё, кроме своего каталога. Исходящий трафик не режем — приложению нужны
goszakup, Telegram и Google.

Логи: `journalctl -u goszakup-monitor -f`.

### Файлы, которые не переезжают

`install.sh` не копирует `.venv` (он от Windows), `settings.local.json` (токены
вводятся заново в админке на сервере) и базу. Память об отправленном начнётся
с чистого листа — при первом проходе придут все актуальные лоты.

## Что выяснено о площадке (эксперименты 2026-07-17)

Документация расходится с реальностью в нескольких местах, поэтому всё проверено
живыми запросами.

### 1. «0 заявок» через API получить нельзя

В API нет поля «количество заявок» ни у `Lots`, ни у `TrdBuy`. Заявки лежат в
`TrdApp` (фильтр `buyId`) → `AppLots.lotId`.

**`TrdApp` отдаёт записи только по объявлениям с заполненным `itogiDatePublic`**
(итоги опубликованы). Проверено: у 40 из 40 объявлений с видимыми заявками итоги
уже опубликованы; у активных — ноль без единого исключения. Это соответствует
закону: заявки конфиденциальны до вскрытия.

Наивная реализация показывала бы «0 заявок» **у каждого** активного лота
и слала бы менеджерам всё подряд под видом нулевой конкуренции.

### 2. Счётчик открыто показан на публичной странице

Страница `goszakup.gov.kz/ru/announce/index/{id}` содержит строку
`Кол-во поданных заявок: N` — вживую, во время приёма заявок.

| Способ закупки | Метод | Счётчик на странице |
|---|---|---|
| Запрос ценовых предложений (ЗЦП) | 3 | **Есть**, живой |
| Открытый конкурс | 2 | **Есть**, живой |
| Из одного источника | 6 | Нет (там и конкуренции нет) |

Проверено вживую: конкурс `17309662` → 2 заявки, конкурс `17319355` → 0 заявок
(статус «Опубликовано (прием заявок)», до конца 2 дня 21 час, итоги не опубликованы).
ЗЦП с близким дедлайном дают разброс 0/1/2/4 — счётчик живой и различающий.

**Покрытие наших позиций: ~95%** (ЗЦП 66% + открытый конкурс 29%).
Скрыто только «из одного источника» (5%) — неконкурентная процедура.

Закон закрывает *содержимое* заявок до вскрытия, но не их количество.
Поэтому источник счётчика — страница, а не API.

> Осторожно при парсинге: если формировать список id через shell, Windows-перевод
> строки (`\r`) попадает в URL и страница молча не парсится. Выглядит как
> «счётчика на портале нет». Это ложный вывод — счётчик есть.

### 3. Дедлайнов на выходных практически не бывает

Из 3272 будущих дедлайнов: будни ~1000/день, **суббота 18, воскресенье 7**.

Буквальное окно «24–48 часов» об это ломается:

- запуск в **пятницу** → окно = сб+вс → находит примерно ничего;
- лот с дедлайном в **понедельник** → попадает в окно в сб/вс → уведомление уйдёт
  в выходной, менеджер увидит его в понедельник утром, когда осталось 0–2 часа.

Около 50% всех дедлайнов приходится на пн/вт, то есть промах массовый.
Окно должно учитывать рабочие дни, иначе система будет молча пропускать ровно то,
ради чего затевалась.

### 4. Ловушки API

- **`publishDate` в фильтре молча игнорируется** — просишь за 10 июля, получаешь
  за 17-е. Не фильтрует, а делает вид.
- **Фильтра по `endDate` нет вообще** — окно отбирается на нашей стороне, обходом
  страниц через курсор `after` (по убыванию `id`).
- **Статус протухает**: объявления со статусом 220 «приём заявок» встречаются
  с дедлайном в прошлом. Фильтровать по статусу нельзя, только по `endDate`.
- `Lots.enstruList` — это `[Int]` внутренних id, а не коды вида `620129.000.000003`.
- Площадка регулярно отваливается по таймауту → в клиенте ретраи с backoff.

### Перепроверка

Правила выше — фундамент системы, и площадка может их изменить.
`app/diagnose.py` перепроверяет каждое: кнопка «Запустить диагностику» в админке
либо `.venv\Scripts\python -m app.diagnose`.
